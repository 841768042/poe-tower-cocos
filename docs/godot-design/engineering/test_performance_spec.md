# 测试、性能与质量门槛

状态：DEMO 权威验证契约。

## 1. 测试分层

### 纯 C# 单元测试

项目：`tests/POETower.Tests`。算法级测试不得依赖运行中的 SceneTree；Node 生命周期与组件协作放入 Godot 集成测试。两类测试都使用固定内容夹具、显式时钟和命名随机流。

必须覆盖：

- CSV DTO 转换后的领域校验；
- Stat 修正顺序、Override 冲突和钳制；
- 伤害、抗性、暴击和击杀归属；
- 感电积累、利用、消费和同 tick 竞争；
- 冻结/眩晕控制韧性和嘲讽持续；
- 目标过滤、排序、锁定和稳定同价；
- Dijkstra 流场、可达性、同价方向和路径版本；
- 冰墙合法性、到期和同 tick 合并重建；
- 地面聚合、浅水扩散和同类取强；
- 建造、升级、复制配置、出售和金币曲线；
- 波次状态机、暂停、1×/2×；
- 掉落两轴、命名随机流、词条排他组、T9→T1 与第三波教学保底；
- 真实物品实例、六槽新档、定义 ID 确定性迁移、背包/快照和 `Flat`/`Increased` handler；
- 奖励幂等、pending 自动恢复、波前检查点、主动退出、存档迁移和故障恢复。

### 内容编译测试

- 所有权威 CSV 能生成目录且哈希稳定；
- 重复 ID、悬空外键、非法枚举、地图断路、候选非 10 个等负例逐项失败；
- 掉落权重/范围、T 级顺序、品质容量、第三波保底、玩家 IIR 数量越权、未登记 handler、`.tres` 稳定 ID 和未启用 Rare/Unique 投放等负例逐项失败，并报告文件/行/列/字段；
- 重新排列无 order 语义的输入行不会改变生成哈希；
- 生成目录再次加载后与编译内存模型等价。

### Godot 集成测试

通过专用 `tests/integration/TestRunner.tscn` 或等价无头入口验证：

- AppRoot 启动、目录和表现资源装载；
- Gameplay 场景创建/释放/重复进入；
- 领域事件正确生成和回收表现 Node；
- 暂停与2倍速不影响 UI 输入；
- UI 命令错误码映射；
- 存档主档/backup/tmp、pending 和波前检查点的路径及平台原子替换适配器；
- 场景切换后没有重复事件连接或遗留 RunSession。

### 可玩烟雾测试

固定种子脚本完成：新档 → 进入地图 → 建塔 → 开波 → 第三波教学掉落 → 胜利 → pending 故障注入 → 重启 → 奖励存在且只存在一次；以及失败/主动退出 → 重启 → 临时奖励不存在；以及当前波异常中断 → 重启 → 从波前检查点确定性恢复。

### 视觉测试

在 1080×1920 与 540×960 检查：建造格触控、路线预览、辅助宝石 10 选 5、特殊怪预告/详情、掉落三层反馈、失败损失、背包比较、暂停和弹窗；颜色之外的轮廓/边框/角标必须可读。

## 2. 确定性

- 测试记录 `run_seed`、内容哈希和输入命令序列。
- 相同环境下最终 Run 摘要哈希必须一致：金币、城墙、实体计数、击杀、掉落 ID、塔配置、波次状态。
- 随机系统按名称派生子流：`combat_crit`、`loot.quantity`、`loot.quality`、`loot.base`、`loot.affix_select`、`loot.affix_roll`、`monster.affix`、`wave_variant`。
- 新增随机流不能改变已有流的结果。

## 3. 性能场景

固定种子场景：

- 100 个活跃敌人；
- 12 座塔；
- 200 个投射物；
- 48 个非空地面效果格；
- 2 段冰墙每 2 秒交替变化，用于压力而非正常平衡；
- 1080×1920，60FPS目标。

记录：模拟 Step 平均/P95/P99、导航重建耗时、渲染帧、分配字节、GC 次数、Node 数和显存/内存趋势。

## 4. 性能预算

| 指标 | 门槛 |
|---|---|
| 画面 | 正常 DEMO 60FPS；压力场景 P95 帧时 ≤16.7ms |
| 逻辑 | 30Hz；单 Step P95 ≤4ms，P99 ≤8ms |
| 导航 | 单次所有 DEMO 移动配置重建 <4ms |
| 分配 | 稳态模拟热路径每 Step 目标 0B；无法避免者必须有测量与上限 |
| GC | 正常 15 分钟单局不得因热路径产生可感知停顿 |
| 内存 | 连续进入/退出 Gameplay 10 次后常驻对象不持续增长 |
| 地面效果 | 48格批处理不得执行每来源×每敌人的笛卡尔扫描 |

预算在目标开发机建立基线；若硬件改变，保留机器说明和历史结果，不只报告“感觉流畅”。

## 5. 性能实现约束

- 导航按移动配置共享流场，不为每敌人 A*。
- 空间关系只在塔阵/地形变化时重算。
- 地面效果按格聚合，每 0.25 秒批处理。
- 目标候选使用空间桶/网格索引，不允许每塔每 tick 全场扫描作为最终实现。
- 热路径不使用 LINQ、反射、字符串标签、日志插值或临时集合。
- Godot 表现池必须完整 Reset；只基于 Profiler 决定池化对象。

## 6. CI 门槛

建议流水线顺序：

1. `dotnet format --verify-no-changes` 或项目确定的格式检查；
2. ContentCompiler 编译全部 CSV；
3. 验证生成文件无未提交差异；
4. `dotnet build`；
5. `dotnet test` Core 测试；
6. Godot `--headless --editor --quit` 导入/解析检查；
7. Godot 集成烟测；
8. 性能场景在专用任务中运行并保存报告。

命令的实际可执行路径和参数在工程初始化时写入代码仓库脚本，CI 与本地共用，不复制两套流程。

### DOC-LOOT-001 本地验收入口

- `tools/verify-demo.ps1` 在内容编译后先检查 `dotnet build` 退出码，失败时立即停止，随后以实际 sandbox 编排 Q53-01 至 Q53-13；
- `LootFeedbackSandbox.tscn` 验证死亡位置掉落、落地、飞入托管、三项摘要、音效请求和 `12 active + 32 queued` 的表现上限；
- `LootPerformanceSandbox.tscn` 使用 100 个真实 Active Enemy，记录 900 个 30Hz Step 的平均/P95/P99、分配和清理结果到 `user://validation/loot_performance_report.json`；经人工确认的交付证据快照保存在 `artifacts/validation/`，标准回归不会改写仓库证据；
- `LootVisualAcceptanceSandbox.tscn` 必须使用实际渲染驱动运行（不能使用 `--headless` 的 Dummy Renderer），输出 540×960 与 1080×1920 的背包和战斗战利品截图到 `artifacts/visual/`，由人工检查遮挡、裁切、字号与层级。

## 7. 缺陷严重度

- P0：存档损坏/重复奖励、无法完成关卡、确定性破坏导致规则错误、最后通路被封、崩溃。
- P1：核心流派失效、状态/金币错误、明显卡顿、UI 阻塞主要操作。
- P2：反馈不清、局部布局、非核心数值和表现问题。
- P3：不影响理解和完成的装饰问题。

P0/P1 清零才能交付 DEMO；P2 必须有明确记录和接受决定。

## 8. 功能完成定义

一项功能只有在以下均满足时完成：

- 配置字段、默认值和校验已完成；
- Core 行为和失败路径已实现；
- Godot 表现、UI和错误反馈已连接；
- 自动测试覆盖关键规则；
- 暂停、2×、重启、场景重复进入无残留；
- 性能符合预算或有已批准的测量结论；
- 权威文档与代码一致。
